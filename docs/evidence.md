# gaishi の根拠: 「作業は英語、報告は日本語」は妥当か

最終更新: 2026-10-06 / 対象バージョン: 0.3.0
想定用途: **コーディング、デザイン系(HTML 生成、スライド作成)**

gaishi の設計意図は次の2点です。

- **H1 トークン削減**: 作業を英語で行うことで、日本語より少ないトークンで済ませる。
- **H2 性能向上**: モデルにとって支配的な言語(英語)で作業させることで、精度を上げる。

加えて、設計上の前提として **H3** を置いています。

- **H3 報告品質**: 最終報告だけを日本語にしても、ユーザー体験は損なわれない。

## 結論(用途別)

| | 評価 | 理由 |
| --- | --- | --- |
| **H1 トークン削減** | **支持される。ただし効果は限定的** | 日本語は英語の約 1.9〜2.6 倍のトークンを使う。一方、コーディングではトークンの大半がコードとツール出力で言語に依存しない。削減できるのは、エージェントが書く自然言語(メモ、指示、検索クエリ)だけ。その割合は未測定。 |
| **H2 性能向上(コーディング)** | **根拠は弱い** | 言語依存の小さいタスクでは差がほぼ出ない(SWE-Bench: −1.3%)。コード生成は言語間で転移し、日本語のタスクでは日本語プロンプトが最良の場合もある。 |
| **H2 性能向上(調査・要件解釈など言語依存の高い工程)** | 支持される | GAIA で −10〜−12%、英語への翻訳で一部回復。 |
| **デザイン系の成果物** | **英語化の対象外** | 画面やスライドに載る文面は日本語のまま直接書くべき。英語で下書きして翻訳すると、文字量の変化でレイアウトが崩れる。 |
| **H3 報告品質** | 直接の研究なし | 設計判断。 |

つまりこの用途では、gaishi の主な価値は **「トークン(コスト)の削減」と「作業指示・調査の英語化」** です。**精度向上を売りにするのは、現時点の根拠では過大**です。成果物(UI 文言、スライド本文)は英語化せず、日本語で直接書く方針に 0.3.0 で変更しました。

## 前回版の訂正

0.2.0 時点の本資料では、MAPS ([Hofman et al.](https://arxiv.org/abs/2505.15935)) を「英語で動くとエージェントの性能が上がる根拠」の1つとして挙げていました。これは誤解を招く書き方でした。Table 4 では、**言語依存の大きい GAIA は −12%、ASB は +14.6%(悪化)だが、コーディング系の SWE-Bench は −1.3%、数学の MATH は −0.1% でほぼ変わらない**と報告されています。コーディング用途では、この論文は英語化の利点をほとんど示していません。

## 確認方法について

- 各論文は arXiv / ACL Anthology / OpenReview の実在を確認しました。会議名は、確認できたものだけ記載しています(確認できなかったものは arXiv と表記)。
- **本文を読んで数値を確認したもの**: Shi et al. の Table 3、Petrov et al. の Table 1、MAPS の Table 2〜4、Terminal-Bench-LILT の本文。
- **アブストラクト(または公式ページの要約)を確認したもの**: それ以外すべて。本文の追試はしていません。
- 数値は論文の記載をそのまま引用しています。私による再計算は「実測」と明記した箇所だけです。
- 2026 年に公開された論文は、査読を経ていないプレプリントを含みます。

## H1: トークン削減

| 論文 | 確認できた内容 |
| --- | --- |
| Petrov et al., [Language Model Tokenizers Introduce Unfairness Between Languages](https://arxiv.org/abs/2305.15425), NeurIPS 2023 | 英語に対する日本語のトークン長の比(Table 1, FLORES-200): GPT-2/RoBERTa 系で **3.00 倍**、ChatGPT/GPT-4 の `cl100k_base` で **2.30 倍**。 |
| Ahia et al., [Do All Languages Cost the Same?](https://aclanthology.org/2023.emnlp-main.614/), EMNLP 2023 | 従量課金の API では、トークン化の非効率な言語の話者ほど多く課金され、結果も劣る傾向がある(22言語、アブストラクトの主張)。 |

**実測(非公式)**: 技術的な作業報告・エージェント指示・レビューコメントの3種類の対訳(筆者作成)を `tiktoken` で数えました。

| トークナイザ | 英語 | 日本語 | 日本語/英語 |
| --- | --- | --- | --- |
| `cl100k_base` | 167 | 427 | 2.56 |
| `o200k_base` | 167 | 318 | 1.90 |

**解釈と限界**

- 日本語は英語の約 **1.9〜2.6 倍**のトークンを使います。新しい語彙ほど差は縮みます。
- 実測は3サンプルだけで、OpenAI 系トークナイザのみです。**Claude や Gemini など他社トークナイザでの数値は未検証**です。
- コーディングや HTML 生成では、トークンの大半は**コード、ツール出力、成果物そのもの**で、言語の影響を受けません。英語化で減らせるのは、メモ・サブエージェントへの指示・検索クエリなどの自然言語部分だけです。
- 成果物に日本語を含む場合(スライド本文、UI 文言)、そのトークンは減らせません。
- skill 自体にもコストがあります。`SKILL.md` の本文は約 930 トークン(`o200k`)、日本語レイアウトの参照ファイルは約 670 トークンで、後者は HTML・スライドなど必要なときだけ読み込まれます。**短い単発タスクでは削減分より読み込みコストが大きくなり得ます**。

## H2: 性能向上

### コーディング

| 論文 | 確認できた内容 | 示唆 |
| --- | --- | --- |
| Hofman et al., [MAPS](https://arxiv.org/abs/2505.15935), EACL 2026 Findings | 4つのエージェント系ベンチマークを11言語に翻訳(日本語を含む)。Table 4: **SWE-Bench −1.3%**(統一バックボーンでは −0.3%)、MATH −0.1%、一方 GAIA −12%、ASB +14.6%。性能低下は、入力に含まれる自然言語トークンの割合と相関。 | コード修正のように言語依存が小さいタスクでは、英語化の利点はほぼない。 |
| Saito et al., [Why We Build Local LLMs](https://arxiv.org/abs/2412.14471), COLM 2025 MELT ワークショップ | 日本語のコード生成の能力を上げるのに、日本語テキストでの追加学習は不要。コード生成・算術推論は言語間で転移し、日本語知識の QA や英日翻訳は転移しない。 | プログラミング能力は言語に依存しない。 |
| Tokumasu et al., [A Study on the Impact of Natural Language Differences in Prompts on Automatic Code Generation](https://arxiv.org/abs/2609.18311), Empirical Software Engineering(採択) | 英語・日本語・中国語のプロンプトで、GPT-4o、o3-mini、DeepSeek-V3.2、Llama-3、Qwen2.5-Coder、Copilot を評価(AtCoder、LeetCode、BigCodeBench)。**各データセットが公式にサポートする言語で精度の中央値が最高**(AtCoder は英語と日本語が高かったと報告されている)。翻訳による改善は、データセットとモデルによって一定しない。 | 日本語で書かれた仕様を、英語に翻訳すれば良くなるとは限らない。 |
| Afrin et al., [LLMs for Code Generation from Multilingual Prompts](https://arxiv.org/abs/2607.14816), arXiv 2026 | GPT-4o mini、DeepSeek、Claude、460 タスク(Python・Java)、中国語・ヒンディー語・スペイン語・イタリア語に翻訳。**英語プロンプトが常に最良の機能的正しさ・コード品質を出すわけではない**。生成コードのコメントや文字列リテラルに、英語とプロンプトの言語が混ざることが多い。 | 日本語は対象外。コメントと文字列の言語は明示して指定する必要がある。 |
| Wang et al., [Exploring Multi-Lingual Bias of Large Code Models](https://arxiv.org/abs/2404.19368), arXiv 2024 | 9つのコードモデルで、**中国語の指示では Pass@1 が少なくとも 13% 低下**。 | 2024 年時点のコードモデルが対象で、最新モデルには当てはまらない可能性が高い。 |
| Kim et al., [Terminal-Bench-LILT](https://arxiv.org/abs/2608.28641), arXiv 2026 | 日本語を含む10言語・300タスク。国際化、文字コード、正規化、文化的慣習に絞る。最強モデルでも合格率 63.1%。結果は一般的なコーディングベンチの順位と相関しない。日本語はモデル間の差が最大級(上位2モデル間で 13.4 ポイント)。例: 全角幅の計算、異体字セレクタ、NFKC による互換漢字の統合。 | **日本語テキストの扱い自体が、コーディングの独立した難所**。英語化では解決しない。 |

### 調査・要件解釈など、自然言語の比重が大きい工程

| 論文 | 確認できた内容 |
| --- | --- |
| Shi et al., [Language Models are Multilingual Chain-of-Thought Reasoners](https://arxiv.org/abs/2210.03057), arXiv 2022 | MGSM(日本語を含む10言語)で、**英語で推論する (EN-CoT) ほうが、問題と同じ言語で推論する (Native-CoT) より同等かそれ以上**。PaLM-540B・日本語の Table 3: Native-CoT **40.0** / EN-CoT **49.6** / Translate-EN **50.0**(英語問題は 62.4)。 |
| Etxaniz et al., [Do Multilingual Language Models Think Better in English?](https://arxiv.org/abs/2308.01223), arXiv 2023 | 5タスクで、モデル自身に英語へ翻訳させてから解く self-translate が直接推論を一貫して上回る。 |
| Zhang et al., [Don't Trust ChatGPT when your Question is not in English](https://arxiv.org/abs/2305.16339), EMNLP 2023 | 英語以外のプロンプトでは、ChatGPT は意味解釈の少なくとも一部を英語の能力に頼っている証拠がある。 |
| Wendler et al., [Do Llamas Work in English?](https://arxiv.org/abs/2402.10588), ACL 2024 | Llama-2 の内部で、概念表現は他言語より英語に近い。 |
| Huang et al., [Not All Languages Are Created Equal in LLMs](https://arxiv.org/abs/2305.07004), EMNLP 2023 Findings | 英語で考えさせる XLT プロンプトで、言語間の性能差が改善する。 |
| Barua et al., [Long Chain-of-Thought Reasoning Across Languages](https://arxiv.org/abs/2508.14828), ICLR 2026 | 推論モデルでは、En-CoT は規模とともに伸び、Target-CoT は遅れる。差は数学など長い推論ほど広がる。 |
| Hofman et al., MAPS(再掲) | GAIA で英語 47.4% に対し、非英語の平均は 35.8%。非英語入力を事前に英語へ翻訳すると 42% まで回復(エージェントが翻訳を判断する場合は 40.9%)。 |
| Luo et al., [Lost in Execution](https://arxiv.org/abs/2601.05366), ACL 2026 | ツール呼び出しの失敗の主因は、**引数の値をユーザーの言語で生成してしまうこと**。対策を入れても英語水準には戻らない。 |

| 論文 | 確認できた内容 | gaishi への反映 |
| --- | --- | --- |

## デザイン系(HTML 生成、スライド作成)

この用途に直接当てはまる研究は少なく、**英語の指示と日本語の指示でデザイン品質がどう変わるかを比べた論文は、今回の調査では見つかりませんでした**。確認できたのは次の点です。

| 論文・資料 | 確認できた内容 | 示唆 |
| --- | --- | --- |
| Kajita et al., [Presentation Slide Translation and Layout Error Correction by LLMs](https://aclanthology.org/2026.acl-srw.26/), ACL 2026 SRW | 日本語のスライドを英語に翻訳すると、**文字量の変化(テキストの膨張)でレイアウトが崩れ、読みにくくなる**。画像と XML を使った補正で、レイアウトの誤り率 4.1%。 | 英語で下書きして日本語に翻訳する方式は、文字量が変わるためレイアウト崩れの原因になる。**成果物は日本語で直接書く**。 |
| Awal et al., [WebMMU](https://arxiv.org/abs/2508.16763), EMNLP 2025 | 多言語のウェブサイトでの理解・編集・デザインからコードへの変換を評価。モデルは、デザインからコードへの変換で、階層構造と多言語コンテンツの扱いが弱い。 | 多言語(日本語)のページ生成は難所で、生成後の確認が必要。 |
| Si et al., [Design2Code](https://arxiv.org/abs/2403.03163), NAACL 2025 | 484 の実ウェブページで、スクリーンショットから HTML を生成。モデルは視覚要素の再現とレイアウトで劣る。 | 見た目の確認は、レンダリングして行う必要がある。 |
| W3C, [Requirements for Japanese Text Layout (JLReq)](https://www.w3.org/TR/jlreq/), Working Group Note 2020 | 禁則処理、約物の扱い、縦書き・横書き、ルビなど、日本語組版の要件。JIS X 4051 に基づく。 | 日本語レイアウトの要件の一次資料。 |
| MDN, [word-break](https://developer.mozilla.org/en-US/docs/Web/CSS/word-break) | `word-break: auto-phrase` は文節単位で改行する値で、実験的。 | 使うなら段階的な拡張として。 |

HTML、CSS、スライドの具体的な注意点(`lang="ja"`、フォントスタック、文字量の見積もり、レンダリングでの確認)は、`skills/gaishi/references/japanese-layout.md` にまとめました。これらは上の資料と一般的な Web 制作の知識に基づく**実務上のチェックリスト**で、個々の項目の効果を測った論文があるわけではありません。

## H3: 最終報告だけ日本語にする

- 「英語で作業し、母語で報告する」構成そのものを直接評価した論文は、**見つかりませんでした**。
- 間接的な根拠: 非英語の思考を強制すると精度が下がる(Qi)ため、作業は英語のまま、最後にだけ日本語化するほうが安全と考えられます。
- 懸念: 翻訳による情報の欠落、日本語出力への言語混乱(Marchisio)。報告ルール(結論先出し、固有名詞・コード・エラー文は原文のまま、全文日本語)で緩和していますが、**緩和策の有効性は未検証**です。

## skill への反映

0.2.0(前回)

1. ツール引数は英語/言語中立のまま(Luo et al.)。
2. 日本語が本質の素材は翻訳しない(Liu et al.、Tokumasu et al.)。
3. 思考言語を強制しない(Qi et al.)。
4. 最終報告は簡潔・全文日本語(Petrov / Ahia、Marchisio et al.)。

0.3.0(今回、コーディング・デザイン用途の調査を受けた変更)

1. **成果物は日本語で直接書く**(Kajita et al.): UI 文言、HTML のテキスト、スライド本文は、英語で下書きして翻訳しない。コード・識別子・コメントは英語。
2. **コメントと文字列の言語を明示**(Afrin et al.): 生成コードで英語と他言語が混ざるのを避ける。
3. **日本語を含む視覚成果物は、チェックリストに従い、レンダリングして確認する**(Kajita、WebMMU、Design2Code、JLReq): `references/japanese-layout.md`。
4. **日本語テキスト処理の落とし穴を追加**(Kim et al.): 全角幅、UTF-8、NFKC による互換漢字の統合、`len()` が表示幅でないこと。
5. **訂正**: コーディングでの性能向上の根拠は弱い(MAPS の SWE-Bench −1.3%)。skill の説明は、主目的をトークン削減と作業の英語化に置いている。

## 未検証・今後の課題

- 現行モデルのコーディング・HTML・スライド生成タスクでの、gaishi あり/なしの **A/B 評価**(合格率、レンダリング品質の人手評価、総トークン、日本語報告の品質)。数十タスク規模で、同一モデル・同一設定、各条件を複数回実行するのが最低ライン。
- Claude / Gemini など他社トークナイザでのトークン比。
- コーディングエージェントのトークン消費のうち、英語化できる自然言語の割合(実際のセッションログでの測定)。
- 英語の指示と日本語の指示での、HTML・スライドのデザイン品質の差。
- 日本語レポートへの翻訳による情報欠落の測定。
- skill の読み込みコスト(約 930 トークン)を回収できるタスク長の見積もり。

これらは今回のセッションでは実施していません。結果が出るまでは、**「コスト削減と作業の英語化には論文上の裏付けがあるが、コーディングの精度向上は示されていない。成果物は日本語で直接書く」**と読んでください。
